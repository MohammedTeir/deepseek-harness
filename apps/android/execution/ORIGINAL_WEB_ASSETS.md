# Original WebView asset inspection

The Android diagnostic activity loads the actual Vite build from apps/web under the AndroidX WebViewAssetLoader HTTPS origin. Gradle builds the original workspace frontend and packages its output under assets/web, excluding sourcemaps and the experimental preview. The activity is private and opened from the existing diagnostic host. This is a static asset inspection, not an integrated application.

The original browser entry requires the host-generated __ModuleLoader__ facade, __DSH_BOOT__ graph, client plugin bundles and live transport. Those are not provided by this activity, so the original boot error is expected and original screens, streaming and runtime operation remain unverified. Gate 4 is IN PROGRESS. The next milestone is to qualify the existing web profile's boot graph and dynamic bundle delivery, then authenticate the original transport before enabling network access.

The asset handler serves only files under the packaged web directory, rejects traversal and API paths, denies non-GET or foreign-origin resource requests, disables file/content access and mixed content, and applies a connect-src none policy. Missing assets return 404. SPA fallback is not implemented. No JavaScript bridge or credentials are supplied. Android WebView origin, CSP, navigation, links and negative cases still require device instrumentation; compilation is not security verification.

## Original host bootstrap evidence

The original built web profile was exercised on Linux with the existing test-only roster observer. The [host result](../evidence/original-web-host-boot.json) records a real host-generated boot graph and successful retrieval of its revisioned client batches after the browser token exchange. The [host test](../tests/web-bootstrap.host.spec.mjs) validates the graph with the original manifest parser and checks that every graph entry belongs to exactly one fetched same-origin batch. No Android runtime or WebView was used in this test; the observer and automated host setup are test fixtures, and the host graph cannot be assumed valid for an Android profile.

The existing client module registry injects the bootstrap facade and graph and serves client batches under /plugins. Browser connection uses the original launch-token-to-cookie exchange and Host/Origin checks for API and WebSocket upgrades; the multiplexed remote stream uses /api/remote.mux. The Android AssetLoader origin differs from the loopback host, so cookie scope, cross-origin policy and WebSocket authentication require a verified transport design. The diagnostic activity keeps its network restriction until that design and denial tests work. The current sdk-minimal Android profile does not establish that the complete web composition or its native dependencies can start on Android.

The host API test sends a request without the session cookie, an authenticated request with the appassets origin, and an authenticated request with a foreign origin. The original host returns 401, 403 and 403 respectively. This is Linux HTTP evidence for the existing trust fence, not an Android WebSocket or cross-app security test. A proposed Android carrier must preserve those denial properties and separately verify WebSocket upgrades, cookies and app-to-app access.

The [host trace summary](../evidence/original-web-host-trace.json) is generated by the [trace auditor](../scripts/audit_web_host_trace.py). It counts successful absolute checkout reads across the Vitest runner and Web profile process tree and records observed native addons. It deliberately excludes relative paths and does not separate test-runner dependencies from runtime dependencies. The summary is not a complete dependency graph or evidence that a Linux addon works on Android; a separately isolated Web profile trace and Android ABI audit are still required before packaging it as an Android runtime.

The [isolated host trace](../evidence/original-web-profile-isolated-host-trace.json) selects the built `dsh --profile web` process and descendants by process identifier, checks the successful launch and requires every recognized child trace. It excludes the Vitest parent, but retains the test-only observer in the web profile. The selection counts absolute successful `openat` reads only; it cannot establish missing relative-path reads, every syscall, a minimal closure, or Android compatibility. Its Linux addon must never be packaged as an Android binary. The [auditor](../scripts/audit_web_host_trace.py) fails on an unrecognized root or a missing recognized child trace.

## Bounded host composition experiment

A [host-only overlay](../tests/fixtures/web-host-bounded.patch.yml) disables six named original host rows that need Android-specific consideration: subprocess, both desktop sandbox providers, open-in-app, automatic directory picker and MCP manager. The [host test](../tests/web-bounded-profile.host.spec.mjs) starts the original `web` profile with this overlay, confirms each exact row has no active fiber, retrieves the actual boot graph and client batches, and repeats the 401/403 origin checks. The [result](../evidence/original-web-bounded-host.json) is Linux host evidence only; it records 74 client entries and three batches for that execution. No model request or Android runtime was exercised.

The host `open-in-app` row is disabled while the original client `ui-open-in-app` entry is active. Whether its controls are shown or how they behave was not tested. Missing providers must be surfaced truthfully before any Android use. Preset-scoped services and other paths require separate review; this overlay is not a sandbox, trusted authorization boundary or production Android composition. The image validator excludes this overlay, its host test and the associated host test configuration from Android interpreted images.

The [bounded composition trace](../evidence/original-web-bounded-host-trace.json) selects the original web-profile process and recognized descendants, and verifies that the exact host-only overlay was present in the root launch. It retains the test observer and the same absolute-path and syscall limitations as the isolated host trace. Its observed Linux addon is not an Android artifact, and the trace is not a complete or minimal Android image. An Android-compatible runtime build, provider capability mapping, preserved approvals and authenticated transport are still required.


## Dependency-closure and Android image work queue (2026-11-14)

The current evidence narrows the next milestone but does not yet identify a complete runtime image. The isolated/bounded traces select the original Web Profile process and recognized descendants, yet count only successful absolute-path `openat` reads and retain a test-only observer. A zero count for relative successful reads is not evidence that relative reads do not occur.

### Required trace and analysis coverage

- Capture and classify relative and absolute `open`, `openat` and `openat2` operations, including successful and failed outcomes where available.
- Observe metadata and access checks (`stat`, `fstatat`, `access`, `faccessat`), directory enumeration, symlink resolution, `realpath`, and file-descriptor inheritance/use.
- Record dynamic module imports, CommonJS resolution, `dlopen` and native addon loads with resolved paths and ABI identity.
- Include configuration, certificates, locale/data files, templates, runtime-generated files, child-process executables and files accessed by recognized descendants.
- Separate the Web Profile process tree from the test runner, test observer, fixtures and development tooling. Preserve raw traces and report exactly which operations are not observable by the instrumentation.
- Combine runtime observation with static import/asset analysis and explicit manifest review. Do not label the result complete or minimal until the blind spots have been addressed and independently checked.

### Image construction and validation

- Build an explicit Android ARM64/Bionic runtime allowlist; reject Linux GNU/GLIBC artifacts, test-only files, source maps, previews and unapproved executables.
- Validate every packaged ELF machine, interpreter, DT_NEEDED dependency, symbol resolution, Android API requirement and alignment. Require Android-built native addons or keep their provider disabled.
- Include a manifest of source revision, build inputs, included paths, hashes, native ABI metadata and license/notice references.
- Add negative tests for path traversal, unexpected file classes, Linux native binaries, missing dependencies and manifest/hash mismatch.
- Rebuild deterministically and compare manifests/hashes before calling the image reproducible.

### Current limitation

The bounded Linux host run disabled six provider rows, but its client graph still contained an active `ui-open-in-app` entry. The Android UI must represent unavailable capabilities truthfully; a disabled backend provider must not leave an apparently functional action. No Android runtime startup, secure WebView transport or original chat flow is established by the current host evidence.
