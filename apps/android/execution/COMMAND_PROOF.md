# Original Harness fixed-command qualification

Scope: APK #3's bounded original-profile tool, native human approval and fixed pwd proof. [Build inspection](../evidence/runtime-command-apk3-build.json) establishes packaging; [executed checks](../evidence/command-integration-validation.json) distinguish host results from unexecuted Android assertions. Gate 2 remains BLOCKED until physical acceptance. This is not general shell/PTY support or the original Web UI milestone.

## Original execution and persistence

The command-smoke controller starts the existing public SDK and sdk-minimal profile with the existing no-execution overlay. A second explicit patch adds the original user-approval and command services and the reviewed Android qualification plugin. Readiness requires the plugin marker; activation failures cannot fall through to an unintended model request. The original agent opens a genuine turn, and its pre-step extension invokes an original registered command that dispatches android_qualified_pwd through ctx.tools.execute. Original guards, schema validation, native tool executor, tools/pre-execute and ApprovalService remain in control. The pipeline's ask reaches the original SDK approval/request callback, which asks the native broker and returns only its outcome. No model response, fake LLM server or replacement loop is used.

Core tool/call and tool/result events describe model-requested steps; fabricating those events here would falsely attribute qualification calls to a model response. Instead the original command/run and command/done lifecycle stores the canonical actual tool batch, alongside the original turn-enclosed approval/asked and approval/decided events. The result traverses the normal tool-result pipeline before the command stores it. A new original runtime resumes the same session and inspects those records through another registered command inside its pre-step hook. Exact recovered records and JSONL hashes must match. This is qualification-triggered execution, not an LLM-generated tool call or demonstrated model-visible tool history.

## Native authorization and process ownership

CommandProbeService is unexported in its own ordinary app process. It derives the canonical private workspace, session identity, two call IDs and UID natively. The AF_UNIX abstract listener checks SO_PEERCRED UID/PID and a random per-run secret. There is no TCP listener or JavaScript bridge. Version, duplicate fields, bounded UTF-8/JSON, exact field sets and native-fixed command/workspace/call bindings reject malformed or changed requests; caller-supplied UID fields are rejected. The Node-side secret is not a defense against malicious same-UID code.

The socket permits describe, prepare, execute and cancel, never approve. Prepare asks the private bound Activity to render native-derived /system/bin/pwd, no arguments, canonical directory, session, call, app UID and requested action. Only the Activity's explicit Approve once or Deny Binder callback can decide the native CommandGrant; the service checks Binder sending UID. Requests expire, duplicate prepare fails and owner shutdown revokes consent. Cancellation closes pending grants and owned processes. Leaving or recreating the Activity cancels this proof rather than restoring approval silently. Approval UI rendering and Android lifecycle behavior remain uninspected until phone testing.

CommandGrant compares immutable request fields and consumes before spawn. FixedPwdExecution uses the native-fixed system executable, no shell string or caller-selected Android executable, cleared environment, closed stdin, bounded wait/output and OwnedProcess termination/reaping. The broker checks workspace ownership, canonical identity, non-root app UID, immutable executable and absence of set-ID bits. A launch failure consumes consent. Two concurrent requests from the genuine tool body must yield one success and one USED response; an additional replay must reject. Native observed starts must equal one. Actual stdout, stderr and exit status return through the original tool result; no fabricated success substitutes for a failure.

## Security limits and unverified cases

Reviewed bundled qualification code is the trust scope. Android process separation under one UID does not isolate files, credentials, Node APIs or tool policy from a hostile plugin. The broker secret is available to the reviewed runtime; it is not a sandbox boundary against that runtime. No arbitrary plugins, package installers, root or Termux provider are enabled. A separate-UID attacker test, general descendant cleanup under OS termination, API 29/recent-device coverage, background execution and full lifecycle recovery remain unverified. A successful fixed pwd proof cannot establish those capabilities.

The real Android negative instrumentation class CommandBrokerTest checks unauthenticated input, malformed/duplicate JSON and an unsupported approval action without granting execution. Its source and test APK compile, but no connected device executed it. It does not replace native human approval testing. Host policy tests exercise expiry/revocation/mutations, 32 consumers, actual Linux pwd, stderr/nonzero exit, timeout, cancellation and changed directory handling. The relocated original-profile host check uses an explicitly automated decision/transport fixture and a real Linux pwd process; that fixture is excluded from the Android image and is not phone or human evidence.

## Phone test tutorial

Install the APK from the [verified delivery record](../evidence/runtime-command-apk3-delivery.json) as an update to the larger Harness runtime proof app. Preserve app data: do not uninstall, clear storage or use the separate small atomic proof app. If Android reports an incompatible signature/update, stop and retain the error instead of deleting sessions. The archive contains one installable app; the instrumentation companion is not required for this manual test.

1. Open Harness runtime proof and select Run original tool + native approval proof, the new fourth diagnostic action.
2. Read the introduction and tap Start test. Keep the app visible throughout.
3. In the first Native command approval dialog, inspect the exact command, no arguments, directory, session/call and ordinary UID. Tap Deny.
4. In the second dialog, inspect the new call ID and the same fixed command/workspace. Tap Approve once. There is no blanket approval.
5. Wait for complete JSON, then tap Copy complete result and return it for review. A BLOCKED result remains a failure; preserve the entire output.
6. Retain screenshots of the approval details if possible. Repeat the complete proof without clearing data to check a fresh broker/session/secret and preserved prior records. Separately leaving the app during a prompt must cancel the run and must not resume execution without a new test and consent.

The successful JSON must show originalRegistryAndPipeline and sessionRecoveredAcrossRuntimeRestart true, original rejected/allowed-once outcomes, actual pwd stdout/exit, nativeConcurrentConsumers 2, nativeConcurrentRejections 1, nativeBroker.processLaunches 1, all negative rejections and unchanged recovered event records. gate2Passed intentionally remains false until review; modelRequestExecuted stays false without test credentials. UI details, physical attribution and residual limitations must be reviewed alongside parser output.

With an explicitly selected connected device, install the main and instrumentation APKs with adb install -r, then run the negative-only class with adb shell am instrument -w -e class io.github.mohammedteir.deepseekharness.CommandBrokerTest ai.deepseek.harness.android.runtimepoc.test/androidx.test.runner.AndroidJUnitRunner. Do not automate the positive human decision. Validate a saved manual JSON using python3 apps/android/scripts/validate_command_result.py RESULT.json --build-record apps/android/evidence/runtime-command-apk3-build.json. Parser fixtures are not physical evidence.
