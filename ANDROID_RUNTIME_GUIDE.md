# Android runtime investigation

## Summary

Investigation and bounded runtime qualification record. APK #2 has accepted user-reported physical profile/session recovery; APK #3 has accepted user-reported fixed-command/native-approval evidence within the Gate 2 local scope. The root manifest requires Node >=24.9.0. Node 24.22.1's `BUILDING.md` explicitly calls Android unsupported and untested in its CI, despite retaining `android-configure`. This is a feasibility risk, not proof that a port is impossible.

[Node source guidance](https://github.com/nodejs/node/blob/v24.22.1/BUILDING.md#android) and [retrieved platform references](audit/android/platform-references.json) support the candidate comparison in [architecture](ANDROID_ARCHITECTURE.md). The local source headers are investigation inputs, not evidence that Android Node executes.

## API and binary requirements

The source index records filesystem/fs-promises, crypto, networking/TLS/DNS, streams, workers, VM, SQLite, process/child_process, TTY, async hooks, inspector, SEA and other builtins. The synchronized PTC evaluator also imports `node:domain`; qualify its evaluator/error path if that plugin is included. Their presence across the repository does not make each mandatory for the minimum profile. Trace imports and the actual chosen plugin tree before excluding a builtin. `node:sqlite` and native session locks are concrete persistence dependencies; browser shims do not establish equivalent semantics.

AArch64 ELF is necessary but insufficient: verify Android/Bionic linkage, public NDK symbols at API 29, DT_NEEDED, interpreter where applicable, addon N-API/V8 compatibility, packaged-library access, 16 KB segment/ZIP alignment and actual load/execute behavior. A glibc or musl Linux ARM64 binary is not an Android binary. Native addon platform selection can fail even after successful C cross-compilation.

Android NDK r28c's `pty.h` declares openpty/forkpty since API 23, so API availability alone does not block API 29. Actual app access, SELinux, child lifecycle and node-pty loading remain unverified. Probe existing APIs before designing a custom PTY bridge.

## Deferred proof

Compare shared-library and packaged-executable candidates using identical device tests before selecting a runtime. Capture exact source/toolchain, compiler/linker output, ABI/API/device identifiers, errors and lifecycle results. Real source/APK builds pass, and the user reports partial Android Node execution ending at a native-addon loader failure. Full API qualification, Harness initialization, persistent sessions and tool results remain unverified. Earlier prototypes do not pass any device acceptance criterion.

## Phase 2 source-build experiment

Gate 1 accepts a bounded shared-library experiment; Gate 2 remains unverified. `apps/android/runtime/build-node.sh` verifies the pinned Node 24.22.1 archive checksum, requires NDK 28.2.13676358 and compiles for Android ARM64/API 29. Set `ANDROID_NDK_HOME` and an absolute `ANDROID_NODE_BUILD_DIR` outside the checkout. Existing matching source/build output can be reused. Host generators use `-O1`; Android target release flags remain intact. The prior `-O0` attempt failed V8 always-inline compilation and is not a successful build result.

Two traceable external-source patches link the NDK CPU-feature implementation into zlib and disable unsupported V8 trap handling (including the cross-build host simulator). Their source is under `apps/android/runtime/patches`; forward/reverse dry runs reject mismatched input and recognize applied patches. Node, NDK CPU-feature, NDK runtime and original system-addon notices must accompany distributed binaries.

`build-system-addon.sh` compiles unchanged upstream flock C source as a Node-API v8 Android shared library. The API probe uses that original binding to attempt acquisition, contention and release; v1–v5 loaded that original binding directly. V6 exercises the updated upstream JavaScript selector described below; Android session integration remains unverified.

After successful compilation, `scripts/package_node.py` checks ARM64 ELF, LOAD alignment, allowed dependencies and the Node entry symbol before staging libraries and license records. Asset preparation requires matching native hashes and refuses an APK without the inspected runtime. JNI loads the library in a dedicated nonexported service process; disposal terminates that process to release V8 globals. This process shares the app UID and is not an isolation boundary against hostile plugins. The probe has no arbitrary command/script input and does not start Harness.

The fixed script tests SQLite, workers, ESM, crypto, private-file output and the native binding; DNS/TLS target only public example.com without credentials. Linux execution verified the local APIs but DNS returned EAI_AGAIN, leaving DNS/TLS unverified. The later v5 user-reported phone results below cover this fixed API/addon probe on one device. No physical device is attached to the developer environment; broader linker and native-addon compatibility remains unverified. Do not report a packaged or compiled probe as an authentic Harness session or approved tool result.

The shared-library host must also qualify `process.execPath` and child-Node launch. `packages/subprocess/subprocess-local/src/runner-launch.ts` uses that path for the managed Node runner; in an embedded Android process it may identify the application process executable rather than Node. The probe records the actual value and marks child-Node launch untested. Do not treat successful worker_threads execution as evidence for child_process.fork or runner launch. A packaged executable or a deliberate Android runner adapter may still be needed.

`build-node-executable.sh` prepares the alternative using the unchanged, checksum-verified Node `src/node_main.cc`, rather than another agent entrypoint. Its ARM64/API 29 compilation and linking passed after shared-library completion. Inspection confirms Android's `/system/bin/linker64`, `$ORIGIN` library search and 16 KB LOAD alignment. V5 includes it in the APK and requests extraction by Android's installer into nativeLibraryDir, not copying it into app-writable storage. The [v5 phone record](apps/android/evidence/phone-v5-user-results.json) reports installed execution, correct process.execPath and child stdout/exit passing on Android 11/API 30. The [architecture decision](ANDROID_ARCHITECTURE.md) selects this for the next bounded profile experiment; other Android releases and lifecycle behavior remain unverified.

The shared-library source build and normal JNI API-probe APK assembly now pass. `apps/android/evidence/runtime-apk-build.json` records source archive, raw library and packaged-library hashes, ELF checks, APK signatures/alignment and notices. AGP strips libraries, so packaged hashes differ from the inspected build inputs; the actual APK libraries were inspected separately. This is build evidence only. The diagnostic APK has no Harness profile or replacement agent and does not satisfy Gate 2.

Diagnostic version 2 captures native Node stderr before calling Start, including module-loader failures before the script runs. The fixed keyless script also writes its last stage and actual exception when possible. The Android host retains a failed exit and displays bounded stderr/result text instead of discarding it. Capture is restricted to the one-shot runtime process and app-private files. Host descriptor and real Node-denial tests passed; build evidence is separate in `apps/android/evidence/runtime-diagnostics-build.json`. The resulting user transcript identifies the native-addon resolution failure below; it does not pass full Android qualification.

The v2 phone transcript narrows this failure to missing `napi_create_function` resolution during addon loading. The symbol is exported by Node, but the original Android addon build lacked a direct Node dependency. Candidate version 3 links the original C binding with `-l:libnode.so -Wl,-z,defs`; no original binding source is modified. The packager requires the explicit DT_NEEDED edge and verifies Node exports. Asset preparation requires the new linkage record. ELF checks reject the actual old addon and accept the new one; these are host checks, not proof of Android loader success. Other native addons must be qualified independently. The v1–v5 production flock selector rejected Android; v6 adds an experimental carrier loader. Successful direct loading in the older probes did not establish session integration.

The user's v3 result reaches serialization after the lock checks, then fails on missing process.getuid. Node's src/node_internals.h deliberately excludes Android from POSIX credentials; bootstrap omits the corresponding methods. Instrumentation retains non-root/app-UID assertions through the native identity source. Upstream getuid/geteuid consumers need separate review; the probe adapter does not port them.

V4's user-reported full JSON passes every fixed API result, including real lock contention/release and DNS/TLS, but records app_process64 as execPath. V5 compares a real packaged Node process with that JNI mode. The fixed executable script checks its own /proc/self/status identity, launches the same installed Node binary for a fixed child script, verifies stdout/exit/identity, then awaits the original API probe. LD_LIBRARY_PATH is limited to the native directory supplied by Android for the app's installed libraries. No caller-supplied command or module path is accepted.

The Linux host reference uses the original same-version public SDK to launch dsh's sdk-minimal profile, create state and recover it after runtime restart. No model request is made. Reproduce with `node apps/android/tests/host-profile-reference.mjs /tmp/android-host-profile-reference.json` after workspace artifacts are built. Android profile loading still needs the genuine dependency closure packaged, device verification of this selector and profile/session startup. Ownership-sensitive spill cleanup remains excluded; broader ownership adapters and shell/PTY integration are unresolved.

## Original lock selector and bounded profile

V6 packages the compiled original `native/system/packages/entry/src/flock.ts` as `harness-flock.mjs`; asset preparation builds that native workspace entry before copying its exact emitted bytes. On Android ARM64 the lazy selector loads only `libharness_system.so` through the carrier linker namespace. It has no new environment-variable override, compile fallback or success fallback. Unsupported architectures and missing bindings reject acquisition. Both fixed Node modes now call its public tryLockExclusive entry and require acquisition, contention rejection and reacquisition. The result identifies nativeLockProvider as upstream-system-entry; no profile or command approval is inferred.

The `apps/android/runtime/profile/no-execution.patch.yml` overlay retains the original sdk-minimal agent, provider, tool registry, working-directory tool and JSONL services while disabling subprocess, PTY, bash/pwsh and image-file tool rows. It does not mount spill-local, whose missing-geteuid ownership fallback remains unqualified. This composition is for startup/session qualification only, is not a security sandbox and does not implement a command provider or root policy. V7 now packages this bounded startup/session composition; its Android execution is still unverified.

The host reference accepts `node apps/android/tests/host-profile-reference.mjs /tmp/android-no-execution-profile.json --no-execution`. That executed mode checks the real composed configuration, starts the original profile through the public SDK and recovers a nondefault working directory after runtime restart. The [host record](apps/android/evidence/host-no-execution-profile-reference.json) is separate from Android evidence. The [v6 build record](apps/android/evidence/runtime-session-lock-build.json) pins the APK and exact original-entry asset; on-device execution of that updated entry remains unverified.

## V7 bounded original-profile image

The third native action uses the installed Node executable to run `apps/android/runtime/profile-smoke.mjs`. This controller drives the existing public SDK, whose same-version dsh CLI initializes the original profile/plugin tree. No replacement loop or model server exists. The proof initializes, writes a working-directory event to real JSONL, awaits runtime shutdown, starts a new runtime, resumes that session and checks its directory. A private checkpoint lets a later invocation verify previous session recovery too. Only explicit executed evidence can establish an app restart; the result leaves appRestartVerified false.

`package_profile.py` uses strace on a real original-profile reference and collects only successful source-tree read opens and contained module aliases. It rejects credential files, unknown native payloads, changed bytes and path escapes. The complete Phase 1 graph is not replaced by this observed subset. Native Linux flock and require-builtin bindings enter only a separate temporary Linux validation tree. Its modules and state live outside the checkout, and runtime environment inheritance is restricted. APK assets contain the interpreted image, hashes and licenses, not those Linux binaries.

Android extracts only interpreted data to a fresh app-private directory, validates the APK-owned archive digest, every member digest and contained paths, then creates the declared module aliases. Native libraries remain in Android's installer directory. Cleanup removes aliases without following them. The fixed service is unexported, checks actual parent/PID/UID and installed execPath, bounds the controller to 90 seconds and gives the original SDK time to close its children. Forced process death and descendant cleanup on Android remain unqualified; this is not an isolation sandbox or background-execution guarantee.

The original Cordis resolver requires node-addon-require-builtin. The pinned source builds its real N-API v9 backend against Bionic; the private optional-package entry loads a fixed SONAME and lets the upstream custom loader validate actual metadata. The controller first requests the real internal ESM loader and records binding identity before starting dsh. Missing private symbols, unsupported machine-code patterns or loader errors must fail, not select guessed offsets or a fake module. Full source revision/build details and both added MIT notices accompany the APK.

## V8 recovery failure investigation

SDK close performs a best-effort protocol shutdown and then reaps the process even when that request fails. The diagnostic now requires sessionPersistence in its SDK-row injection list and uses an explicit acknowledged shutdown before closing each runtime. A failure therefore stops at its actual shutdown error instead of silently proceeding to a missing-session lookup. The additional runtimeStderr read API returns the existing bounded stderr tail plus SDK shutdown-failure notes; it neither consumes logs nor changes cleanup. Its output is untrusted and not automatically redacted. This keyless proof captures only its fixed runtime's notes, truncates retained text and lists only its private test session directory, not session contents.

The storage preflight exercises the same required POSIX primitives independently: directory fsync, file write/fsync, hardlink-based exclusive publication, EEXIST rejection and inode/content identity. A failed primitive blocks the proof rather than enabling a weaker fallback. Inventories after the first acknowledged shutdown and before resume compare Dirent and lstat directory observations. The original JSONL backend, file format and agent engine are unchanged. The [real Linux permission experiment](apps/android/evidence/host-sdk-shutdown-failure.json) proves that a failed persistence operation can be hidden by ordinary close; it does not identify the Android cause.
