# Android runtime investigation

## Summary

Investigation record, not installation instructions for a working runtime. The root manifest requires Node >=24.9.0. Node 24.22.1's `BUILDING.md` explicitly calls Android unsupported and untested in its CI, despite retaining `android-configure`. This is a feasibility risk, not proof that a port is impossible.

[Node source guidance](https://github.com/nodejs/node/blob/v24.22.1/BUILDING.md#android) and [retrieved platform references](audit/android/platform-references.json) support the candidate comparison in [architecture](ANDROID_ARCHITECTURE.md). The local source headers are investigation inputs, not evidence that Android Node executes.

## API and binary requirements

The source index records filesystem/fs-promises, crypto, networking/TLS/DNS, streams, workers, VM, SQLite, process/child_process, TTY, async hooks, inspector, SEA and other builtins. The synchronized PTC evaluator also imports `node:domain`; qualify its evaluator/error path if that plugin is included. Their presence across the repository does not make each mandatory for the minimum profile. Trace imports and the actual chosen plugin tree before excluding a builtin. `node:sqlite` and native session locks are concrete persistence dependencies; browser shims do not establish equivalent semantics.

AArch64 ELF is necessary but insufficient: verify Android/Bionic linkage, public NDK symbols at API 29, DT_NEEDED, interpreter where applicable, addon N-API/V8 compatibility, packaged-library access, 16 KB segment/ZIP alignment and actual load/execute behavior. A glibc or musl Linux ARM64 binary is not an Android binary. Native addon platform selection can fail even after successful C cross-compilation.

Android NDK r28c's `pty.h` declares openpty/forkpty since API 23, so API availability alone does not block API 29. Actual app access, SELinux, child lifecycle and node-pty loading remain unverified. Probe existing APIs before designing a custom PTY bridge.

## Deferred proof

Compare shared-library and packaged-executable candidates using identical device tests before selecting a runtime. Capture exact source/toolchain, compiler/linker output, ABI/API/device identifiers, errors and lifecycle results. Real source/APK builds pass, and the user reports partial Android Node execution ending at a native-addon loader failure. Full API qualification, Harness initialization, persistent sessions and tool results remain unverified. Earlier prototypes do not pass any device acceptance criterion.

## Phase 2 source-build experiment

Gate 1 accepts a bounded shared-library experiment; Gate 2 remains unverified. `apps/android/runtime/build-node.sh` verifies the pinned Node 24.22.1 archive checksum, requires NDK 28.2.13676358 and compiles for Android ARM64/API 29. Set `ANDROID_NDK_HOME` and an absolute `ANDROID_NODE_BUILD_DIR` outside the checkout. Existing matching source/build output can be reused. Host generators use `-O1`; Android target release flags remain intact. The prior `-O0` attempt failed V8 always-inline compilation and is not a successful build result.

Two traceable external-source patches link the NDK CPU-feature implementation into zlib and disable unsupported V8 trap handling (including the cross-build host simulator). Their source is under `apps/android/runtime/patches`; forward/reverse dry runs reject mismatched input and recognize applied patches. Node, NDK CPU-feature, NDK runtime and original system-addon notices must accompany distributed binaries.

`build-system-addon.sh` compiles unchanged upstream flock C source as a Node-API v8 Android shared library. The API probe uses that original binding to attempt acquisition, contention and release; the production Harness lock selector still rejects Android and is not modified by this experiment.

After successful compilation, `scripts/package_node.py` checks ARM64 ELF, LOAD alignment, allowed dependencies and the Node entry symbol before staging libraries and license records. Asset preparation requires matching native hashes and refuses an APK without the inspected runtime. JNI loads the library in a dedicated nonexported service process; disposal terminates that process to release V8 globals. This process shares the app UID and is not an isolation boundary against hostile plugins. The probe has no arbitrary command/script input and does not start Harness.

The fixed script tests SQLite, workers, ESM, crypto, private-file output and the native binding; DNS/TLS target only public example.com without credentials. Linux execution verified the local APIs but DNS returned EAI_AGAIN, leaving DNS/TLS unverified. Android behavior, including linker namespace and addon loading, is unverified. No device is attached. Do not report a packaged or compiled probe as an authentic Harness session or approved tool result.

The shared-library host must also qualify `process.execPath` and child-Node launch. `packages/subprocess/subprocess-local/src/runner-launch.ts` uses that path for the managed Node runner; in an embedded Android process it may identify the application process executable rather than Node. The probe records the actual value and marks child-Node launch untested. Do not treat successful worker_threads execution as evidence for child_process.fork or runner launch. A packaged executable or a deliberate Android runner adapter may still be needed.

`build-node-executable.sh` prepares the alternative using the unchanged, checksum-verified Node `src/node_main.cc`, rather than another agent entrypoint. Its ARM64/API 29 compilation and linking passed after shared-library completion. Inspection confirms Android's `/system/bin/linker64`, `$ORIGIN` library search and 16 KB LOAD alignment. V5 includes it in the APK and requests extraction by Android's installer into nativeLibraryDir, not copying it into app-writable storage. Android loading, process.execPath and child behavior remain device tests before selecting this runtime approach.

The shared-library source build and normal JNI API-probe APK assembly now pass. `apps/android/evidence/runtime-apk-build.json` records source archive, raw library and packaged-library hashes, ELF checks, APK signatures/alignment and notices. AGP strips libraries, so packaged hashes differ from the inspected build inputs; the actual APK libraries were inspected separately. This is build evidence only. The diagnostic APK has no Harness profile or replacement agent and does not satisfy Gate 2.

Diagnostic version 2 captures native Node stderr before calling Start, including module-loader failures before the script runs. The fixed keyless script also writes its last stage and actual exception when possible. The Android host retains a failed exit and displays bounded stderr/result text instead of discarding it. Capture is restricted to the one-shot runtime process and app-private files. Host descriptor and real Node-denial tests passed; build evidence is separate in `apps/android/evidence/runtime-diagnostics-build.json`. The resulting user transcript identifies the native-addon resolution failure below; it does not pass full Android qualification.

The v2 phone transcript narrows this failure to missing `napi_create_function` resolution during addon loading. The symbol is exported by Node, but the original Android addon build lacked a direct Node dependency. Candidate version 3 links the original C binding with `-l:libnode.so -Wl,-z,defs`; no original binding source is modified. The packager requires the explicit DT_NEEDED edge and verifies Node exports. Asset preparation requires the new linkage record. ELF checks reject the actual old addon and accept the new one; these are host checks, not proof of Android loader success. Other native addons must be qualified independently. The production flock selector still rejects Android; successful direct loading would not yet establish session integration.

The user's v3 result reaches serialization after the lock checks, then fails on missing process.getuid. Node's src/node_internals.h deliberately excludes Android from POSIX credentials; bootstrap omits the corresponding methods. V4 reports missing getuid and null Node uid, with separate Android UID/PID fields from android.os.Process after matching the runtime PID. It does not polyfill global process methods. Instrumentation retains non-root/app-UID assertions through the native identity source. Upstream getuid/geteuid consumers need separate review; the probe adapter does not port them.

V4's user-reported full JSON passes every fixed API result, including real lock contention/release and DNS/TLS, but records app_process64 as execPath. V5 compares a real packaged Node process with that JNI mode. The fixed executable script checks its own /proc/self/status identity, launches the same installed Node binary for a fixed child script, verifies stdout/exit/identity, then awaits the original API probe. LD_LIBRARY_PATH is limited to the native directory supplied by Android for the app's installed libraries. No caller-supplied command or module path is accepted.

The Linux host reference uses the original same-version public SDK to launch dsh's sdk-minimal profile, create state and recover it after runtime restart. No model request is made. Reproduce with `node apps/android/tests/host-profile-reference.mjs /tmp/android-host-profile-reference.json` after workspace artifacts are built. Its actual executed result is separate from all Android evidence. Android profile loading is still blocked on qualifying executable launch and adapting the original Android-incompatible native selector, ownership checks and shell/plugin composition.
